Kubernetes Architecture

Compressed from Lesson 1. Source of truth: kubernetes.io — Kubernetes Components.

On this page

The split

A cluster is one or more control plane machines making global decisions, plus one or more nodes running the actual workloads. In minikube both roles live on one VM/container, but the roles are logically distinct.

Control plane

ComponentJob
kube-apiserverFront door. All reads/writes (incl. kubectl) go through it.
etcdKey-value store; the cluster's single source of truth.
kube-schedulerAssigns new Pods to a node based on resources/constraints.
kube-controller-managerRuns control loops that reconcile actual state → desired state.

Node

ComponentJob
kubeletAgent per node; ensures containers in its Pods are running & healthy.
kube-proxyMaintains network rules so Services route to the right Pods.
Container runtimeActually runs containers (e.g. containerd).

The core loop

You declare desired state (via the API server) → controllers notice a gap → scheduler places new Pods → kubelet on the target node makes it real → controllers keep checking, forever.

This declarative reconciliation loop is the single idea underneath almost everything in Kubernetes: Deployments, Services, autoscaling, self-healing.

Pod, in one line

The Pod is the smallest deployable unit — one or more containers that share a network namespace (same IP, localhost between them) and can share storage volumes. You almost never manage a Pod directly; a controller (e.g. Deployment) manages Pods for you.

Glossary anchors

Control loopA controller's watch → compare → act cycle that drives actual state toward desired state.
Desired stateWhat you declared (in a manifest); Kubernetes continuously works to make actual state match it.
NodeA worker machine (VM or physical) that runs Pods.
