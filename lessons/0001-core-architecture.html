Control Plane vs Node

Every CKAD task you'll eventually do — and every architecture question an interviewer asks — assumes you know this split. It's the one diagram to have fully internalized before anything else clicks.

On this page
Primary source
Read Kubernetes Components (official docs, ~5 min). For a narrated walkthrough, TechWorld with Nana's Kubernetes Tutorial for Beginners covers the same split visually in its first 15 minutes.

The split

A Kubernetes cluster has two kinds of machines. The control plane makes global decisions about the cluster (scheduling, detecting failures) but runs none of your application code. Nodes are where your containers actually run.

Control plane

kube-apiserver — the front door. Every read/write, including every kubectl command, goes through it.

etcd — key-value store holding all cluster state. The single source of truth.

kube-scheduler — watches for new unscheduled Pods and picks which node they run on.

kube-controller-manager — runs the control loops that notice "actual state ≠ desired state" and fix it.

Node

kubelet — the agent on each node. Talks to the API server, makes sure the containers described for its Pods are actually running.

kube-proxy — maintains network rules so a Service's traffic reaches the right Pods.

Container runtime — the software that actually starts/stops containers (e.g. containerd).

In minikube, both roles run on the one VM you start — but they're still logically separate, and kubectl always talks to the control plane, never directly to a node.

The one idea underneath everything

You declare desired state → a controller notices a gap between desired and actual → the scheduler places any new Pods → the kubelet on the target node makes it real → controllers keep checking, forever.

This is declarative reconciliation. Deployments, self-healing, autoscaling — all of it is this same loop applied to different resources. When you're stuck debugging later, "which part of this loop is broken?" is usually the right first question.

The Pod, briefly

The Pod is the smallest deployable unit: one or more containers that share a network namespace (same IP; they can reach each other over localhost) and can share storage volumes. You'll almost never create a bare Pod in practice — a controller like a Deployment manages Pods on your behalf. That's the next lesson.
